# 实施拆解与验收记录

## 原计划的落地方式

原计划按 96 小时学习周期组织；本次先交付可运行代码与可复现实验，再保留接板练习。五个工作包之间的依赖为：协议/计算 → 队列/网络 → 回放验证 → 策略实验 → 只读解释。ESP32 与 VMware 可以并行准备。

| 阶段 | 本地实现 | 验证方法 |
|---|---|---|
| 1. C 基础及 TCP | `linux/src/core.c`、`main.c`，严格协议、POSIX socket/poll | 严格警告编译、数值参考、TCP 分帧测试 |
| 2. 队列与调度 | 单 worker、mutex/condition、有界指针队列、FIFO/priority | 单测验证稳定排序，黑盒验证队满及非抢占 |
| 3. 设备接入 | ESP-IDF Wi-Fi STA、非阻塞 TCP、超时、退避、合成数据 | host 编码测试与跨端解析；无线/开发板仍需接板 |
| 4. 实验 | 固定合成 workload、两策略交替重复、逐任务原始 CSV | 同输入哈希和条件、每次分组指标、实际发送迟到 |
| 5. 只读助手 | 两个固定文件读取工具，规则型解释 | 无数据不下结论、无 shell/控制工具、与 C 独立运行 |
| 6. Linux 环境 | 当前目录内独立 Ubuntu VMware VM，NAT | guest 内实际构建、集成测、实验与工具版本记录 |

## 设计取舍

- 使用纯 C/POSIX 和 Python 标准库，减少学习与部署依赖；ESP32 使用 ESP-IDF。
- 两种策略使用相同数组队列，容量默认 32、最大 4096，priority 线性寻找最早紧急任务，单次 O(n)。适合第一版的小规模实验，保留易解释性。
- 按完整消息进入解析器时记录接收时间，避免把 TCP 传输延迟误叫排队等待；单调时钟避免系统校时影响。
- 非法帧、超长、残帧和队满都是明确拒绝；已接受任务在正常信号退出时排空。强杀/断电不提供持久化恢复。
- 不提供应用 ACK 或 exactly-once。读 CSV 才能确认完成，设备序号只用于追踪，断线不重发不确定帧。
- 数据文件与状态写入失败将使服务失败退出，不掩盖实验记录丢失。
- 只读助手默认采用规则解释；新增 `ask --backend llm` 可选接入模型，仍只暴露这两个固定、无参数的只读工具，数值由统计脚本计算。接口、预算和失败回退见 [Agent 使用说明](agent.md)。模型凭证仅由使用者显式配置，本次测试不调用真实模型 API。
- 原始仓库仅包含规划 README，提交 `15d5c43` 保留为实现前的基线。源码、测试、复现说明及小型验收证据一同纳入版本控制；虚拟机、SDK 缓存、密钥及本地网络配置保留在本机。

## 验收证据

最终实际测试结果记录在 `docs/validation.md`。不能把“已写测试”“CI 已配置”当作“已运行通过”。开发板构建和硬件验收分别记录。

接板后的剩余步骤：

1. 确认 ESP32 具体型号，在 ESP-IDF 中设置 target、Wi-Fi、VM 可达 IP。
2. 编译/烧录并保存串口启动日志，验证 Linux 出现对应 device_id/seq。
3. 停止并重启服务、断开再恢复 Wi-Fi，检查重连、发送继续、序号及丢帧记录。
4. 调整负载验证拒绝事件，保留原始 CSV、固件参数和实验环境信息。
5. 录制服务启动、设备发送、策略报告和只读解释的短演示；将合成数据标注放在画面或说明中。

## 学习顺序

先读 `edge_parse` 与 `edge_compute`，用 GDB 检查一个任务；再读 `EdgeQueue`、worker 的条件变量循环；随后看 `poll` 和 `EdgeFramer`，观察一次 recv 与一条消息的区别。最后跑两种策略，手算一个小输入的滑动平均及一组延迟的 P95。这样每一阶段都有可以独立解释和验证的结果。
